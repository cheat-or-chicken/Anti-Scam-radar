# 防詐 Agent 分析與示警審查（dialogue-v4）

## 結論

執行流程已能完整完成，對明確不合理金融操作有辨識能力，但早期示警、風險降級與預測命中的語意驗證尚不可靠。先前「三例通過」僅表示匯款前有warn且正常案例無warn，不能等同逐輪推論皆正確。

本次只審查既有結果，沒有修改prompt、規則或重新呼叫模型。依據：reports/dialogue-v4三例結果，以及最新網頁B1工作階段d78e03f0ca0d4d25a9cd4efc6002fd18。驗證網頁B1與批次B1的訊息前綴完全相同、prompt hash相同。

## 示警合理性

### B1：首次示警不是最有力證據點

- 批次第8則因「實名認證」即warn，並聲稱一般寄送不會需要認證。這是不受本次對話支持的泛化。當時應保留疑點、建議獨立查證，不能僅據此定為明確危險。
- 最新網頁第8–14則維持monitor較合理；第15則因凍結壓力與轉銀行專員warn，是可疑組合，可作查證提醒，但仍須區分與已明確不合理金融要求的強度。
- 第18則「請先開啟網路銀行，這一步需要轉帳完成驗證」是清楚的目的／行為不相符，足以支持停止操作的警報。第20則具體指定收款資訊，證據更強。
- 第18則應優先對應R_PAYMENT_PURPOSE；實際常標R_SENSITIVE_ACCESS，付款與向他人交付敏感權限的概念混用。
- 第22則以無卡提款驗證、第24則掃碼付款、第30及32則購買點數／交序號等警報方向合理。

本次人工保守審查：第18則是明確高風險警報的可靠位置，距第21則首次付款為3輪。這是審查基準，不是另一個模型实測數字，也不表示第15則不能做較輕的查證提醒。

### B2：共享畫面與共享網銀要分開

- 第9則買家把帳戶鎖定歸咎使用者，是疑點，但尚不足以證明詐騙；可monitor。
- 第15則要求分享手機畫面，在可疑客服脈絡下值得提醒核實，但尚未明确要求分享銀行資訊。直接稱敏感畫面或套R_SENSITIVE_ACCESS證據偏弱。
- 第17則在既有共享畫面狀態下要求開網銀，足以支持敏感操作警報；引用應同時包含第15/16則的共享狀態及第17則的網銀要求。
- 第19則輸入簡訊碼不是單獨等同交付OTP；風險來自前面的未核實指導與共享網銀畫面，不能遺漏上下文。
- 第23則要求轉帳，與寄件／解鎖目的不符，warn合理。
- 第27–30則套R_ADVANCE_RECOVERY不合理：案例沒有出金、退款或追回款項條件，應保留不相符付款／敏感操作規則。

本次人工保守審查：第17則是明確高風險位置，距第26則匯款為9輪、距第18則已開網銀為1輪。不是模型實測的新提前量。

### N1：不示警合理，但不能宣稱已驗證安全

全26則無warn符合正常交易目標。monitor只是內部狀態，不算詐騙警報。付款對應商品與運費，未出現認證金流或敏感權限要求，因此不示警有理由。

但模型多次直接說「正常平台交易」，平台與出貨實際仍只有聊天自述，應表述為「目前對話未見不合理要求」，不能升格為已查證。加LINE與正常付款後monitor持續多輪但理由沒有指出疑點，內部狀態也略含糊。

## 風險記憶與一致性問題

最新網頁B1第15–33則warn，第34、35則因對方說驗證完成、準備退款而降成monitor，第36則又warn。第34則沒有任何獨立反證消除前面的不合理金融要求；不能因本輪沒有新的要求就降級。

畫面保存歷史警報只能避免資訊消失，沒有修好當前風險判斷。應分開保存「本輪新增訊號」與「案件未解除的風險」，降低案件風險必須指出哪筆證據被何種新事實推翻。

同一B1、相同訊息與prompt，批次首次第8則，網頁首次第15則，相差7輪。完整三例通過不能當成首次示警穩定的證明。

## 預測命中審查

最新網頁B1標示9筆matched、2筆missed、1筆pending；這是系統標籤，不是人工確認準確率。

至少4筆matched不成立：

| 預測 | 系統所用命中訊息 | 問題 |
|---|---|---|
| p5：對方再確認收件資料／提供付款方式 | 第6則使用者問在哪填資料 | 發話者與行為都不符 |
| p24：另一筆付款或驗證操作 | 第25則回報上一筆2,000付款完成 | 舊要求完成不等於新要求 |
| p27：對方再要求付款／拖延 | 第28則使用者詢問退款 | 使用者提問不是對方的新要求 |
| p32：其他驗證資訊／追加款項或序號 | 第33則交付剛剛已索取的序號 | 不是其他或新增要求 |

另外p20、p22明確預測使用者會回報完成，語意上可命中，但不符合產品「預測對方下一步手法」的核心；不應算同一種成果。

p29預測再要求驗證付款，第30則出現購買禮券／點數要求，是較合理的新增行為命中。p17到第18則亦有新要求，但預測措辭較寬泛。

批次N1也把第7則使用者打招呼算成第6則「對方補傳影片」命中，實際影片在第8則。這證明目前的問題跨正常／詐騙情境存在。

程式已驗證引用存在且時間在預測之後，但尚未驗證發話者、是否新行為、是否與預測相同。不能將這些自動matched數字直接放進簡報當預測準確率。

## 建議修正順序

1. 風險狀態分開：新訊號與未解除警報分開，明確反證才可降級。
2. 示警分級：一般查證提醒與明確危險警報分開；早期程序疑點不冒充金融損失證據。
3. 規則需驗必要條件：rule_ids只是模型選擇，現在程式只驗ID存在，未驗整個條件成立。
4. 預測改成actor、action、object、is_new_request與時間窗；先檢查發話者與新舊要求，再判語意命中。
5. 用新的正常客服／合法認證／一般畫面協助案例作對照，凍結版本後重跑評估一致性。

本次未自動變更這些行為，避免把審查與調參結果混為一談。
