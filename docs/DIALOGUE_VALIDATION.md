## dialogue-v5：通用證據與狀態契約

本次沒有修改三份案例、金額、示警輪次標籤或七幕分類，也沒有增加案例 ID、商品名或話術字串分支。

- 正式示警的每個規則，必須用條件編號逐項提供原文輪次、支持狀態及解釋；任何條件標為 unknown 或 contradicted 都拒絕該規則，並說明正常解釋為何不足。程式驗證條件完整性、引用範圍與規則存在；語意成立與否仍由模型判断，並非確定性真偽驗證。
- `monitor` 維持內部觀察，不顯示正式警報。弱訊號不透過加總自動升級。
- 維護 `active_warning`。若模型欲降級但未提出有效格式的誤讀修正或獨立反證，沿用先前警報與原始證據。允許有依據的修正，歷史首次示警仍保留。反證內容是否足夠仍需語意審查。
- 預測只針對已知對方角色的新要求，存 actor、action_type、object；本輪觀察必須符合這三項、為新要求、且有當輪原文才接受命中。使用者付款回報、追問與既有要求的重複不能算新要求。`user` 是既有訊息格式中受保護使用者的角色 ID；未知未來角色不強行預測。
- 無效預測核對不影響有效的風險分析。到期未發生記為 missed，對話結束仍在視窗內保留 pending；這些是系統判定而非人工驗證的準確率。
- 測試新增未解除風險持續、允許誤讀更正、錯角色／錯動作／非新要求拒絕匹配、規則條件不足拒收。

模型與 API 維持原設定。結構化輸出設計參照 [OpenAI 官方文件](https://developers.openai.com/api/docs/guides/structured-outputs)，JSON schema 能限制輸出結構，不能保證語意正確。

開發途中失敗與舊契約試跑保存在 `reports/dialogue-v5/run*`、`repeat*`，不得混入最終版本成效；`final*` 亦屬中間契約試跑，最終試跑使用 `release1`、`release2`、`release3`。每筆都有 prompt hash、版本、原始輸入及輸出可供核對。

尚未解決的品質限制：

- 首次示警仍有1–2則差異。部分模型把「轉帳驗證」歸為敏感權限規則，付款用途規則的引用仍不理想。條件支持狀態也是模型判斷，不能把結構通過當作語意正確。
- 預測核對目前過於保守：九次最終結果皆無接受的命中。逐輪檢查發現語意近似的預測與實際動作也會因 object 字串不一致被拒收。這降低假命中的同時造成漏算，不能宣稱預測品質已通過驗證。後續應以獨立語意核對替代 object 完全相同，保留角色、新要求、時間等硬檢查。
- 正常案例有兩次產生不必要的預測（均未命中），雖然沒有正式示警，預測產生門檻仍需改善。
- 未針對新案例測泛化，三個已知案例的結果不能視為整體準確率。
